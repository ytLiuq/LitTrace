## P1 fixed

### P1-1  TUI was hard-wired to the legacy `handle_chat` path

[tui.py:8](src/littrace/tui.py#L8) imported `handle_chat` directly
and `_handle_input` awaited it synchronously. With `curses.getch()`
blocking, the TUI could not interleave keystrokes with the App
Server's `mcpServer/elicitation/request` notifications — every MCP
tool call was auto-declined at [client.py:947-955](src/littrace/codex_runtime/client.py#L947-L955)
because no UI was installed to handle them. Operators using the
GUI got the worst of both worlds: the legacy UI's chat affordances
but the new App Server's read-only defaults.

**Fix** (4 files):

1. [codex_runtime/client.py](src/littrace/codex_runtime/client.py):
   new `elicitation_handler` opt-in hook on `AppServerClient`. When
   set, `_handle_server_request` calls the handler with the
   notification params and relays the handler's return value as
   the JSON-RPC `result`. When unset, the previous auto-decline
   behaviour is preserved (back-compat with the smoke / turn-trace
   scripts that never opted in).

2. [codex_runtime/service.py](src/littrace/codex_runtime/service.py):
   `chat()` and `_chat_with_client()` now accept
   `elicitation_handler`. The handler is installed on the shared
   AppServerClient via `set_elicitation_handler` immediately
   before `run_turn` and cleared in the `finally` block so a
   subsequent chat on the same shared client does not inherit a
   stale UI hook.

3. [agent_runtime.py](src/littrace/agent_runtime.py):
   `handle_agent_chat` now plumb the `elicitation_handler` kwarg
   through to `CodexAppServerChatService(config).chat(...)`. The
   legacy branch (`mode != "codex_app_server"`) ignores the
   argument; the codex branch forwards it.

4. [tui.py](src/littrace/tui.py): full rewrite. Switched to
   `handle_agent_chat`, switched `curses.getch()` to
   `screen.nodelay(True)` so the main loop can poll the inflight
   task between keystrokes. The chat runs as an
   `asyncio.create_task` whose result writes onto `state` directly;
   the main loop just clears `state.inflight_task` on completion.

   The approval modal is a centered curses box rendered on top of
   the input row when `state.pending_approval` is set. The handler
   parked on `_make_elicitation_handler(state)` parks a Future,
   stashes it on `state.pending_approval`, and awaits the
   operator's Y/N/Esc decision. Y accepts, N declines, Esc
   cancels. The three responses use the codex vocabulary
   `{"action": "accept"|"decline"|"cancel", "content": null, "_meta": null}`
   documented in `_ACCEPT_RESPONSE` / `_DECLINE_RESPONSE` /
   `_CANCEL_RESPONSE`.

   The `finally` block in `run_tui` cancels any inflight task and
   resolves any pending approval with `cancel` so the reader loop
   never blocks on a Future whose owner has already exited.

## Lessons (added to the running list)

9. **Async UI integrations need an opt-in callback, not a hard-wired
   handler**. The previous `_handle_server_request` always
   declined because it had no UI to forward to. Adding a
   `set_elicitation_handler` setter instead of a callback
   constructor argument keeps the headless path zero-cost and
   lets the TUI install the hook at chat time, then clear it on
   chat exit so the shared client does not leak state.

10. **`nodelay(True)` is the right pattern for curses + asyncio**.
    The previous TUI blocked on `screen.getch()`, which made
    interleaving with an `asyncio.create_task` impossible.
    `nodelay(True)` plus a small `asyncio.sleep` tick lets the
    loop poll the task, redraw the screen, and surface mid-turn
    notifications. The CPU cost is negligible because
    `getch()` returns -1 immediately when no key is pending.

11. **Park UI decisions on a Future, not a Queue**. The first
    sketch used an `asyncio.Queue` to ferry the operator's
    decision back to the reader loop. A `Future` is cleaner
    because the reader loop's coroutine awaits exactly one
    value (the operator's single Y/N/Esc decision) and the
    main loop's key handler resolves it exactly once. Queues
    become ambiguous when the same UI instance re-enters the
    modal multiple times.

## What's deliberately NOT done

- The TUI itself is not unit-tested. Curses requires a TTY and
  is best validated by the operator running `python -m
  littrace.tui` against a real session; mocking curses is more
  fragile than valuable. The wiring (handler installation,
  handler clearing, handler return-value relay) IS unit-tested
  through `AppServerClient` and `CodexAppServerChatService` fakes,
  which cover the same code paths the TUI exercises.
- The approval modal does not yet capture the operator's
  free-form `content` field that codex-harness supports. The
  LitTrace MCP tools do not currently surface user-form input
  (the only thing they ask for is server / tool / args), so
  `content: null` is the correct default. A future tool that
  needs free-form text would add a text input row to the modal.
- `set_elicitation_handler` is not thread-safe. The shared
  `AppServerClient` is supposed to be driven from one event
  loop at a time, so this is consistent with the rest of the
  client's contract. Documented by the `set_elicitation_handler`
  docstring.
